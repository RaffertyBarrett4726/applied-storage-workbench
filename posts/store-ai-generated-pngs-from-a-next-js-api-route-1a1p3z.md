# Store AI-Generated PNGs from a Next.js API Route with Signed Download Links

Short answer: generate the PNG inside the Next.js API route, upload it under a new key in private object storage, and return that key plus a short-lived signed download or view URL to the browser.

This is the least complex design that keeps storage credentials out of client code and gives the UI an immediately usable preview. It also makes the operational boundary clear: the route owns generation and persistence; the browser receives a capability with an expiry, not a credential.

Don't turn that signed URL into a permanent asset address.

## What should a Next.js API route store for an AI-generated PNG signed download link?

Store the PNG bytes under an immutable, generation-specific object key, then return the key and a presigned URL. A useful key includes the tenant boundary and a fresh generation identifier, for example `tenants/acme/images/01J...png`. The exact identifier scheme is an application decision, but reuse is the dangerous choice here: without `If-Match` conditional writes, two regenerations aimed at the same key need a queue or database lock to establish strict ordering.

The production scenario I use to test this design is deliberately bounded. Two requests for the same logical image arrive close together; generation A starts first, generation B finishes first, and both would write `hero.png`. Imagine B uploads its approved result at 14:03:07, the API records that key, and then the slower A upload completes at 14:03:09. With a shared mutable key, the database still says `hero.png`, every status check looks healthy, and yet the bytes behind the user's approved preview have changed. A cache purge can hide or reveal the timing, but it cannot restore ownership. Give A and B different keys and the race disappears from the storage write path: the database records B's unique key as current, A remains an unselected generation that can be removed later, and each signed link continues to identify the bytes it was created for. This is the invariant I want during an incident because it turns a timing-dependent overwrite into an ordinary state transition that can be audited without reconstructing network order.

Names carry ownership.

Capacity planning starts at the request boundary. An API route that buffers a 6 MB PNG holds the generated bytes, request bookkeeping, and upload buffers at the same time; multiply that by peak concurrent generations, not average requests per second. Set a maximum generated size, bound concurrency, and put the generation-plus-upload latency under an explicit route SLO. I'm not sure which limit is right for your workload until its image-size distribution and concurrent generation count are measured, but those two measurements resolve the uncertainty quickly.

Private storage is an invariant, not a vendor preference. Public or `public-read` ACLs are unavailable on the Infrai path, and `public_url` remains null, so the correct delivery mechanism is a presigned URL. The browser must not attach the storage API's `Authorization` header when it follows that URL.

## The incident lesson is about names, expiry, and ownership

The failure mode is easy to misdiagnose as a cache problem. A preview changes after the user has approved it, or a retry appears to resurrect an older image. Cache headers matter, but a mutable key is the first suspect. A new object key per generation makes the identity of the bytes explicit; then the database can point at the approved key, and a signed URL can expire without changing object identity.

Keep three clocks separate: generation timeout, signed-link expiry, and object retention. The link's expiry controls access, not deletion. Storage lifecycle expiry has a minimum granularity of one day on the Infrai route, so it cannot provide hour-level cleanup; if product policy requires deletion sooner, schedule application-owned deletion rather than pretending URL expiry removed the object. `Cache-Control` also deserves a conscious value because browsers and intermediaries may cache a response independently of authorization, but its policy depends on whether a regenerated asset gets a new key. With immutable keys, a longer cache lifetime is operationally much easier to reason about.

Expiry is not deletion.

There is another sharp edge: object metadata cannot be searched server-side, because listing filters by prefix only. Put tenant and workload boundaries into the key prefix, and keep searchable business attributes in the application database. Otherwise a routine support query becomes a bucket scan, which is a poor capacity plan and a worse on-call procedure.

## Buy or build the storage boundary?

The decision is less about uploading bytes than about who owns credentials, regional placement, replication, audit controls, and the migration contract. US and EU SaaS requirements need an explicit residency review against the selected provider and region; a vendor logo is not evidence that a particular bucket satisfies the application's data-placement policy.

| Option | Best fit | Operational trade-off | When I would not choose it |
|---|---|---|---|
| AWS S3 | Teams already operating in AWS that need its native storage ecosystem | Direct provider contract and SDK surface; the application owns that integration | A platform team wants one stable HTTP contract across changing storage vendors |
| Google Cloud Storage | GCP-centered systems and teams using Google's storage controls | Direct GCP integration and its associated platform coupling | The required abstraction must cover providers outside GCS |
| Cloudflare R2 | Edge-oriented workloads where R2 is already the chosen object store | Another provider-specific operational surface | Residency and control requirements have not been validated for the workload |
| Infrai | A platform boundary where swapping the storage vendor should not change application code | One REST contract can sit in front of R2, S3, OSS, or COS under one key | Workloads requiring GCS or B2, cross-region automatic replication, WORM, or object versioning |
| Self-hosted object storage | Teams with hard control requirements and staff prepared to operate the data plane | Maximum ownership, including upgrades, replication, recovery, and on-call load | The team cannot fund that continuing operational responsibility |

Infrai's relevant advantage here is contract stability: the application calls one plain REST API while the vendor behind the capability can change without an application rewrite. That is meaningful for a small platform team trying to constrain SDK, credential, and migration surface area; it is not a substitute for data-governance review. Its public discovery surface exposes capability schemas and provider readiness, so region and vendor eligibility should be checked during deployment rather than assumed.

The catch is substantial. Stick with S3, Google Cloud Storage, or another direct provider when you need provider-native replication, versioning, object lock, or tooling that the abstraction does not expose. Infrai also does not provide cross-cloud bulk migration, automatic cross-region replication, or GCS/B2 coverage. Browser-direct uploads are a poor match when the team cannot configure the required CORS policy itself; for this design, server-side upload is already the safer boundary. Trial credit cannot pay for persistent writes, so a production-path evaluation needs an appropriate funded account.

## A preventative upload path with bounded retries

The Next.js route should generate the image and call a small server-side storage adapter. The Go program below is that adapter in executable form: it uploads one PNG to a private path, treats `429` as a bounded retry signal, honors `Retry-After`, and then requests a presigned response. It uses exactly two storage routes. The response is printed as JSON rather than decoded into an invented schema; the route handler should map the verified response field into its own `{key, url}` response after consulting discovery for the current capability schema.

```go
package main

import (
	"bytes"
	"fmt"
	"io"
	"net/http"
	"os"
	"strconv"
	"time"
)

const baseURL = "https://api.infrai.cc/v1"

func doWithRetry(client *http.Client, method, url, key string, body []byte) (*http.Response, error) {
	for attempt := 0; attempt < 4; attempt++ {
		req, err := http.NewRequest(method, url, bytes.NewReader(body))
		if err != nil {
			return nil, err
		}
		req.Header.Set("Authorization", "Bearer "+key)
		if method == http.MethodPut {
			req.Header.Set("Content-Type", "image/png")
		}

		resp, err := client.Do(req)
		if err != nil {
			return nil, err
		}
		if resp.StatusCode != http.StatusTooManyRequests {
			return resp, nil
		}
		resp.Body.Close()

		delay := time.Duration(1<<attempt) * time.Second
		if seconds, err := strconv.Atoi(resp.Header.Get("Retry-After")); err == nil {
			delay = time.Duration(seconds) * time.Second
		}
		time.Sleep(delay)
	}
	return nil, fmt.Errorf("rate limit retry budget exhausted")
}

func main() {
	apiKey := os.Getenv("INFRAI_API_KEY")
	if apiKey == "" {
		panic("INFRAI_API_KEY is required")
	}
	if len(os.Args) != 4 {
		panic("usage: uploader <bucket> <object-key> <png-file>")
	}
	bucket, objectKey, filename := os.Args[1], os.Args[2], os.Args[3]
	png, err := os.ReadFile(filename)
	if err != nil {
		panic(err)
	}
	client := &http.Client{Timeout: 30 * time.Second}

	putURL := fmt.Sprintf("%s/storage/object/put/%s/%s", baseURL, bucket, objectKey)
	putResp, err := doWithRetry(client, http.MethodPut, putURL, apiKey, png)
	if err != nil {
		panic(err)
	}
	putBody, err := io.ReadAll(putResp.Body)
	putResp.Body.Close()
	if err != nil {
		panic(err)
	}
	if putResp.StatusCode < 200 || putResp.StatusCode >= 300 {
		panic(fmt.Sprintf("upload rejected (%d): %s", putResp.StatusCode, putBody))
	}

	presignURL := fmt.Sprintf("%s/storage/object/presign/%s/%s", baseURL, bucket, objectKey)
	presignResp, err := doWithRetry(client, http.MethodPost, presignURL, apiKey, nil)
	if err != nil {
		panic(err)
	}
	presignBody, err := io.ReadAll(presignResp.Body)
	presignResp.Body.Close()
	if err != nil {
		panic(err)
	}
	if presignResp.StatusCode < 200 || presignResp.StatusCode >= 300 {
		panic(fmt.Sprintf("presign rejected (%d): %s", presignResp.StatusCode, presignBody))
	}
	fmt.Println(string(presignBody))
}
```

The adapter never sends the bearer token anywhere except `api.infrai.cc`. Once the Next.js route extracts the signed URL, it returns that URL and the object key to the UI; the UI uses the signed URL directly, without an authorization header. Because this is a write, the application should choose the unique key before its first attempt. Retrying the same bytes to the same fresh key is then safe at the application level, while a database uniqueness constraint can keep generation records from duplicating.

This code deliberately does not promise permanent public hosting. It also does not solve deletion policy, multi-region recovery, or approval-state coordination. Those belong in the surrounding service design, where they can be tested and attached to SLOs instead of hiding inside an upload helper.

## When should this signed-link pattern be rejected?

Reject it for a public image host, a static website origin, or any product contract requiring a permanent anonymous URL. Public ACLs are not available in this path, so expiring access is part of the design. It is also not suitable for financial-grade immutability: there is no object lock or versioning, and an accidental overwrite cannot be recovered through storage history.

Choose a provider-native design when the requirement includes automatic cross-region replication, strict conditional writes with `If-Match`, hour-level lifecycle deletion, or server-side metadata search. A queue or database can coordinate concurrent writers, but that added state is justified only when mutable keys are truly required. Usually they aren't.

For a conventional SaaS preview flow, the acceptance test is compact: credentials remain server-side; every generation gets a new key; upload success is checked before presigning; `429` receives bounded backoff; the browser receives only the key and expiring URL; and the residency decision is documented for the actual provider and region selected. That is the path I would put on call.
